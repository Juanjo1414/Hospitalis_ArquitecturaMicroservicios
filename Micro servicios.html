Arquitectura Basada en Microservicios

El objetivo de este documento WEB explicar qué es una arquitectura basada en microservicios, cómo se organiza, cómo fluye una petición, cómo se comunica entre servicios, cómo se maneja Git y cómo se implementa con ejemplos en Java.

Concepto clave

Microservicios no significa “partir una aplicación en pedazos porque sí”. Significa dividir un sistema por capacidades de negocio, con servicios autónomos, desplegables de forma independiente y preparados para escalar, fallar y evolucionar de manera controlada.

1. ¿Qué es una arquitectura basada en microservicios?

Definición

Una arquitectura basada en microservicios es un estilo arquitectónico donde una aplicación se divide en varios servicios pequeños, autónomos y desplegables de forma independiente. Cada servicio representa una capacidad de negocio concreta, por ejemplo: pedidos, inventario, facturación, usuarios o notificaciones.

  • Cada microservicio tiene una responsabilidad clara.
  • Cada servicio puede tener su propia base de datos.
  • Los servicios se comunican mediante REST, gRPC, mensajería o eventos.
  • Cada microservicio puede desplegarse, escalarse y mantenerse de forma independiente.
  • Requiere disciplina técnica: observabilidad, pruebas, automatización y manejo de fallos.

8. Ejemplo 2: e-commerce

Escenario realista

Una plataforma de comercio electrónico con miles de usuarios necesita escalar pedidos, inventario, pagos, usuarios, envíos, promociones y notificaciones de forma independiente.

Order Service

Crea pedidos, valida reglas de compra y coordina el flujo principal.

Inventory Service

Reserva stock y evita sobreventa cuando hay alta concurrencia.

Billing Service

Gestiona facturación, impuestos, pagos y comprobantes.

User Service

Administra usuarios, perfiles, direcciones y preferencias.

Shipping Service

Calcula envío, guía, transportadora y estado logístico.

Notification Service

Envía correo, SMS, WhatsApp o push notification.

9. Ejemplo 3: banca digital

Caso

Un cliente realiza una transferencia desde una app bancaria. La transacción debe validar saldo, riesgo de fraude, límites, cuenta destino y notificar el resultado.

  • Transaction Service: registra y coordina la transacción.
  • Fraud Service: evalúa riesgo.
  • Account Service: valida saldo y actualiza cuentas.
  • Notification Service: informa resultado al cliente.
Flujo
Cliente → API Gateway → Transaction Service → Fraud Service → Account Service → Notification Service → Response

Este ejemplo permite enseñar resiliencia, idempotencia, transacciones distribuidas, compensaciones y monitoreo de procesos críticos.

10. Ejemplo Java

OrderController.java

Ubicación en Git:

services/ └── order-service/ └── src/ └── main/ └── java/ └── com/ └── universidad/ └── orders/ └── controller/ └── OrderController.java

Rol en la arquitectura:

  • Recibe la petición HTTP desde el API Gateway.
  • Convierte el JSON de entrada en DTO.
  • No debe contener reglas de negocio complejas.
  • En el flujo pertenece al bloque Controller.
@RestController @RequestMapping("/orders") public class OrderController { private final OrderService orderService; @PostMapping public ResponseEntity<OrderResponse> create(@RequestBody CreateOrderRequest request) { return ResponseEntity.ok(orderService.createOrder(request)); } }

OrderService.java

Ubicación en Git:

services/ └── order-service/ └── src/ └── main/ └── java/ └── com/ └── universidad/ └── orders/ └── application/ └── OrderService.java

Rol en la arquitectura:

  • Contiene el caso de uso principal: crear pedido.
  • Valida reglas de negocio propias del pedido.
  • Coordina comunicación con Inventory Service.
  • En el flujo pertenece al bloque Service / Application.
@Service public class OrderService { private final InventoryClient inventoryClient; private final OrderRepository orderRepository; public OrderResponse createOrder(CreateOrderRequest request) { inventoryClient.reserveStock(request.productId(), request.quantity()); Order order = new Order(request.customerId(), request.productId(), request.quantity()); orderRepository.save(order); return new OrderResponse(order.getId(), "ORDER_CREATED"); } }

InventoryClient.java

Ubicación en Git:

services/ └── order-service/ └── src/ └── main/ └── java/ └── com/ └── universidad/ └── orders/ └── infrastructure/ └── client/ └── InventoryClient.java

Rol en la arquitectura:

  • Permite que Order Service se comunique con Inventory Service.
  • Encapsula la llamada HTTP para no mezclar infraestructura con negocio.
  • Debe manejar timeouts, errores y reintentos.
  • En el flujo pertenece al bloque Client / Integration.
@FeignClient(name = "inventory-service") public interface InventoryClient { @PostMapping("/inventory/reserve") void reserveStock(@RequestParam Long productId, @RequestParam Integer quantity); }

OrderRepository.java

Ubicación en Git:

services/ └── order-service/ └── src/ └── main/ └── java/ └── com/ └── universidad/ └── orders/ └── infrastructure/ └── persistence/ └── OrderRepository.java

Rol en la arquitectura:

  • Administra persistencia de pedidos.
  • No debe acceder a datos de otros microservicios.
  • Cada servicio administra sus propios datos.
  • En el flujo pertenece al bloque Persistence.
public interface OrderRepository extends JpaRepository<Order, Long> { }

application.yml

Ubicación en Git:

services/ └── order-service/ └── src/ └── main/ └── resources/ └── application.yml

Rol en la arquitectura:

  • Configura nombre del servicio, puerto, base de datos y discovery.
  • Permite que el servicio se registre o sea localizado.
  • En producción puede ser administrado por Config Server.
  • En el flujo pertenece a Infrastructure Configuration.
spring: application: name: order-service server: port: 8081 eureka: client: service-url: defaultZone: http://localhost:8761/eureka

11. Arquitectura de microservicios aplicando capas

Concepto

Una arquitectura de microservicios también puede organizarse internamente por capas. Esto significa que cada microservicio es independiente, pero dentro de cada servicio se mantiene una estructura ordenada para separar responsabilidades: entrada, lógica de aplicación, dominio, infraestructura y persistencia.

La idea clave es que microservicios define cómo se separa el sistema completo, mientras que las capas definen cómo se organiza internamente cada microservicio.

  • Controller / API: recibe peticiones HTTP.
  • Application / Service: coordina casos de uso.
  • Domain: contiene reglas de negocio y entidades.
  • Infrastructure: integra base de datos, otros servicios o mensajería.
  • Persistence: repositorios y acceso a datos propios del servicio.
Microservicio por capas
Controller / API
↓
Application Service
↓
Domain Model / Rules
↓
Infrastructure / Persistence
Estructura recomendada del microservicio por capas
services/ └── product-service/ └── src/ └── main/ └── java/ └── com/ └── universidad/ └── products/ ├── controller/ │ └── ProductController.java ├── application/ │ └── ProductService.java ├── domain/ │ ├── Product.java │ └── ProductStatus.java ├── infrastructure/ │ └── persistence/ │ ├── ProductRepository.java │ └── ProductEntity.java └── ProductApplication.java
Ejemplo funcional: Product Service

Este ejemplo representa un microservicio encargado de administrar productos dentro de una plataforma de e-commerce. El servicio permite crear productos, consultar productos y validar reglas simples del dominio, como que el precio sea mayor que cero.

Este microservicio podría ser consumido por otros servicios como Order Service o Inventory Service, pero sus datos y reglas internas pertenecen únicamente a Product Service.

ProductController.java

Ubicación en Git:

services/ └── product-service/ └── src/ └── main/ └── java/ └── com/ └── universidad/ └── products/ └── controller/ └── ProductController.java

Rol en la arquitectura:

  • Recibe las peticiones HTTP relacionadas con productos.
  • Expone endpoints como POST /products y GET /products/{id}.
  • No contiene reglas de negocio profundas; delega al ProductService.
  • En el flujo pertenece a la capa Controller / API.
@RestController @RequestMapping("/products") public class ProductController { private final ProductService productService; public ProductController(ProductService productService) { this.productService = productService; } @PostMapping public ResponseEntity<ProductResponse> create(@RequestBody CreateProductRequest request) { return ResponseEntity.ok(productService.createProduct(request)); } @GetMapping("/{id}") public ResponseEntity<ProductResponse> findById(@PathVariable Long id) { return ResponseEntity.ok(productService.findById(id)); } }

ProductService.java

Ubicación en Git:

services/ └── product-service/ └── src/ └── main/ └── java/ └── com/ └── universidad/ └── products/ └── application/ └── ProductService.java

Rol en la arquitectura:

  • Coordina los casos de uso del microservicio.
  • Valida reglas antes de persistir información.
  • Convierte solicitudes en objetos del dominio.
  • En el flujo pertenece a la capa Application / Service.
@Service public class ProductService { private final ProductRepository productRepository; public ProductService(ProductRepository productRepository) { this.productRepository = productRepository; } public ProductResponse createProduct(CreateProductRequest request) { Product product = Product.create(request.name(), request.price()); Product saved = productRepository.save(product); return new ProductResponse(saved.getId(), saved.getName(), saved.getPrice()); } public ProductResponse findById(Long id) { Product product = productRepository.findById(id) .orElseThrow(() -> new RuntimeException("Producto no encontrado")); return new ProductResponse(product.getId(), product.getName(), product.getPrice()); } }

Product.java

Ubicación en Git:

services/ └── product-service/ └── src/ └── main/ └── java/ └── com/ └── universidad/ └── products/ └── domain/ └── Product.java

Rol en la arquitectura:

  • Representa la entidad principal del dominio del microservicio.
  • Contiene reglas propias del producto.
  • Evita que reglas como precio inválido queden en el controller.
  • En el flujo pertenece a la capa Domain.
public class Product { private Long id; private String name; private Double price; private Product(String name, Double price) { if (name == null || name.isBlank()) { throw new IllegalArgumentException("El nombre del producto es obligatorio"); } if (price == null || price <= 0) { throw new IllegalArgumentException("El precio debe ser mayor que cero"); } this.name = name; this.price = price; } public static Product create(String name, Double price) { return new Product(name, price); } public Long getId() { return id; } public String getName() { return name; } public Double getPrice() { return price; } }

ProductRepository.java

Ubicación en Git:

services/ └── product-service/ └── src/ └── main/ └── java/ └── com/ └── universidad/ └── products/ └── infrastructure/ └── persistence/ └── ProductRepository.java

Rol en la arquitectura:

  • Administra el acceso a datos del microservicio.
  • Solo maneja datos propios de productos.
  • No debe consultar bases de datos de otros microservicios.
  • En el flujo pertenece a la capa Infrastructure / Persistence.
public interface ProductRepository { Product save(Product product); Optional<Product> findById(Long id); }

ProductJpaRepository.java

Ubicación en Git:

services/ └── product-service/ └── src/ └── main/ └── java/ └── com/ └── universidad/ └── products/ └── infrastructure/ └── persistence/ └── ProductJpaRepository.java

Rol en la arquitectura:

  • Implementa la persistencia usando Spring Data JPA.
  • Permite desacoplar el dominio de la tecnología de base de datos.
  • Hace parte de infraestructura, no del dominio.
  • En el flujo pertenece a la capa Infrastructure.
public interface ProductJpaRepository extends JpaRepository<ProductEntity, Long> { }

application.yml

Ubicación en Git:

services/ └── product-service/ └── src/ └── main/ └── resources/ └── application.yml

Rol en la arquitectura:

  • Configura el nombre del microservicio.
  • Define el puerto de ejecución.
  • Configura conexión a base de datos propia.
  • En el flujo pertenece a Infrastructure Configuration.
spring: application: name: product-service server: port: 8084 spring.datasource.url: jdbc:h2:mem:productsdb spring.jpa.hibernate.ddl-auto: update
Idea clave: aplicar capas dentro de cada microservicio evita crear microservicios desordenados. Un microservicio separado físicamente también puede convertirse en un problema si internamente mezcla controller, lógica de negocio, persistencia e integración externa sin estructura.

12. Comunicación REST vs eventos

REST síncrono

Se usa cuando el servicio necesita una respuesta inmediata para continuar.

Order Service → Inventory Service Necesito saber si hay stock antes de crear el pedido.
Eventos asíncronos

Se usa cuando otros procesos pueden reaccionar después sin bloquear el flujo principal.

Order Service → Kafka → Notification Service El pedido ya fue creado; enviar notificación puede ocurrir después.

13. Testing en microservicios

Unit Testing

Valida reglas internas de cada servicio.

Integration Testing

Valida base de datos, clientes REST y mensajería.

Contract Testing

Valida que consumidor y proveedor respeten el contrato API.

End to End

Valida el flujo completo, pero debe usarse con moderación.

14. SOLID y bajo acoplamiento en microservicios

SOLID aplicado
  • S: cada servicio tiene responsabilidad de negocio clara.
  • O: se agregan servicios sin modificar todos los existentes.
  • I: APIs pequeñas y específicas.
  • D: lógica de negocio no depende directamente de infraestructura.
Bajo acoplamiento
  • No compartir base de datos entre servicios.
  • No duplicar lógica crítica sin control.
  • No acoplar servicios por clases internas.
  • Usar contratos API o eventos versionados.

15. ¿Cuándo NO usar microservicios?

  • Cuando el sistema es pequeño y puede resolverse con un monolito bien diseñado.
  • Cuando el equipo no tiene experiencia en despliegues, observabilidad, redes y automatización.
  • Cuando no hay necesidad real de escalar partes del sistema por separado.
  • Cuando no existe capacidad para administrar varios repositorios, pipelines y ambientes.
  • Cuando el costo operativo supera el beneficio arquitectónico.

17. Recomendación final

La arquitectura basada en microservicios debe entenderse como una evolución del diseño modular, no como el punto de partida obligatorio. Primero se entienden responsabilidades, capas, cohesión, acoplamiento y dominio. Luego se justifica la separación física en servicios independientes.

Un buen microservicio no es solo un proyecto separado: es una unidad de negocio autónoma, con contrato claro, datos propios, despliegue independiente, pruebas, monitoreo y responsabilidad técnica definida.
